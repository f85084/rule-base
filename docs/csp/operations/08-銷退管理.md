# 銷退管理

## 1. 用途、入口與權限視角

銷退管理用來查詢客戶的退貨／換貨單、查看物流與驗收入庫狀態，以及在允許的狀態下取消、修改取件資料或將換貨改為銷退。現行前端 route 為 `/Return`，明細 route 為 `/return/detail/:id`。

一般專員可查詢與處理畫面顯示的作業；取消、地址審核、退款或其他按鈕是否可用，取決於銷退狀態與目前登入權限。需求資料有地址修改審核、取件人／電話必填等規則，但完整角色矩陣未在目前來源中確認，按鈕以當期 UI 為準（**runtime 未確認**）。

## 2. 正常操作流程

1. 先在客戶接單作業查詢會員，再從【銷退查詢】進入；也可在 `/Return` 輸入頁面提供的查詢條件。
2. 查詢後核對目前客代、訂單／銷退單號、退貨或換貨類型、商品與狀態。
3. 點選銷退單進入明細，查看取件資訊、配送單號、備註與必要的商品明細。
4. 若要操作取消、修改取件、建立客訴或換貨改銷退，先依下一節的狀態條件確認按鈕是否應出現。
5. 完成寫入後回到列表重新查詢，確認狀態、取件資料與關聯客訴是否更新。

## 3. 狀態、欄位與作業邊界

| 狀態／欄位 | 判讀與限制 |
|---|---|
| 銷退受理 | 退／換貨的起始狀態；可見【取消退貨】／【取消換貨】與取件資料【編輯】。 |
| 收回指示 | 物流或廠商已收到收回訊息；來源手冊同樣允許取消與修改取件。 |
| 銷退進行中 | 物流／廠商已開始安排收回，不應假設仍可取消。 |
| 等待驗收入庫 | 商品等待倉庫驗貨；先等待銷退結果，不要重複建立銷退。 |
| 銷退確認 | 退貨完成，系統會回填銷退入庫日。 |
| 銷退取消／銷退中止 | 前者表示既有銷退被取消；後者可能因多次收貨失敗或商品缺損產生，系統可能自動建立客訴。 |
| 取件資料 | 取件人、聯絡電話、地址、要求取件日、時段與備註。需求頁記錄取件人／電話需必填；來源手冊記載電話最多 16 碼、取件日排除週日。 |

換貨訂單只有在「等待出貨」「出貨指示」或「出貨進行中」時，才可使用【換貨改銷退】。成功後原換貨訂單與原銷退單會變更狀態，並新增一般銷退單；完成後應重新查詢三者關聯。

## 4. 資料來源與合併

- 列表由銷退查詢結果提供，明細再依銷退識別值載入銷退資訊與取件資料。
- 從客戶頁進入時，查詢結果可能先要求切換目前服務客戶；切換完成後才重新載入列表。客代是客戶上下文的合併鍵，銷退單／關聯單號是作業資料的識別鍵。
- 配送單號（收回）若以連結顯示，代表可另開貨運端查詢；貨運端進度與 CSP 銷退狀態不是同一來源，兩者不一致時要分開記錄。
- 列表成功但明細或貨運端進度失敗，屬單一請求失敗；不要把整頁空白、查無資料與物流尚未同步混為一談。

## 5. 寫入與副作用

- 【取消退貨／取消換貨】會改變銷退單狀態；確認視窗出現後才送出。
- 修改取件資料會寫入銷退作業資料；取件人與電話通過必填／格式驗證後才儲存，地址若需要審核則依畫面流程處理。
- 【建立客訴】會帶入關聯單號、銷售編號與「銷退」關聯類別，完成後回到銷退明細；客訴建立結果要在[客訴處理](09-客訴處理.md)另行確認。
- 【換貨改銷退】可能同步取消原換貨流程、建立一般銷退、處理退款或發票跨期作業；不要在結果尚未回傳時重複點擊。

## 6. 空資料、部分失敗與錯誤排查

| 現象 | 先檢查 | 判讀與處理 |
|---|---|---|
| 完全無法進入銷退頁 | 登入、目前客戶、共用 API 與頁面錯誤 | 先判斷頁面／權限問題，不要改寫訂單。 |
| 查無銷退單 | 客代、訂單號、退／換貨條件與日期 | 以客代和單號重新查；可能是條件未命中或資料尚未同步。 |
| 狀態有但操作按鈕不見 | 銷退狀態、訂單類型、登入權限 | 依狀態表確認；不要用直接重送請求代替 UI 條件。 |
| 取件資料儲存失敗 | 取件人、電話必填、電話長度、日期是否為週日、備註字數 | 修正欄位後重送；結果不明時先回查，不要重複建立。 |
| 銷退中止但未看到客訴 | 銷退狀態、客訴列表與資料同步時間 | 分別查銷退與客訴；「可能建立」不是已建立的保證。 |
| 換貨改銷退部分成功 | 原換貨單、原銷退單、新一般銷退單及發票提示 | 保留各單號與時間交維運核對，勿再次執行相同操作。 |
