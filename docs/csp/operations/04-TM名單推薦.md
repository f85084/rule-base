# TM 名單推薦

從 CSP 的 TM 名單頁進入後，這裡是電話行銷（TM）專員的外呼工作台，不只是名單列表。使用者可在同一頁查詢名單、開啟客戶資料、查看訂單與互動紀錄、處理待辦，再透過 TM 電話圖示完成外撥與後續小結。

本文件面向一般專員、主管／Admin 與需要協助判讀名單的維運人員。頁面路由為 `/OutboundTMList`；畫面上的實際欄位與可用選項仍以目前環境、權限及業務公告為準。

## 一、權限與查詢視角

| 使用者／來源狀態 | 預設查詢範圍 | 可切換的查詢視角 |
|---|---|---|
| 一般專員（目前來源已確認） | 【被指定人】預設為登入者，只能查詢自己被分派／維運的名單。 | 不應自行切換成其他人員；系統會以目前登入者作為查詢人員。 |
| `Admin`（目前來源已確認） | 預設仍以目前登入者為查詢人員。 | 目前來源確認 `Admin` 可切換查詢人員；這只代表查詢視角可切換，不等同於自動取得所有管理操作。實際可查範圍仍以目前 UI 與授權結果為準。 |
| 主管／管理職／名單管理權限（手冊描述，角色映射待確認） | 手冊描述可查詢其他人員或所有名單，但目前來源未提供職稱到角色的完整對照。 | 手冊描述可清空【被指定人】、選擇其他人員，或不指定人員直接查詢客代；是否可用必須先依目前授權矩陣與 UI 顯示確認，不可只由職稱推定。 |
| 被指定人 | 是本次查詢所選的目標專員，不等於額外授權。 | 查詢結果以該人員的名單範圍為準；若查不到，先確認是否真的分派／維運給該人員。 |

依 MI 完整手冊的描述，主管／管理職在帳號清單太長時可於選擇被指定人視窗以客戶編號縮小人員清單；具名單管理權限者可不指定人員直接查詢客代。這些是手冊描述，實際是否可操作必須以目前授權矩陣與 UI 為準。跨專員查詢多筆客代時，使用【查詢客代／多客代】；一次最多 100 筆，現行手冊另記載輸入的客代須有維運專員才會被查到。

## 二、基本查詢流程

1. 進入 TM 名單，先確認【被指定人】是否為正確的查詢視角。
2. 依目的設定商品、未曾購買、未撥打、預約外撥、LINE 綁定、會員／OB 等級、360、標籤或其他條件。
3. 按【查詢】載入符合條件的一般名單，先確認列表中的客代、姓名、有效日與提醒資訊。
4. 按【名單推薦】查看系統依目前查詢視角與系統推薦機制整理的優先處理名單；本操作手冊不主張所有已設定篩選條件都會套用到推薦結果。推薦結果為空時，先依目前查詢視角與當日推薦資料判讀，不要立即判定頁面故障。
5. 要重新開始時按【清空】。這會清除查詢條件，也會清除【被指定人】；清空後須重新確認查詢視角。

列表中：

- 點客戶編號會另開【客戶查詢】並帶入客代；點客戶姓名會開啟右側客戶資訊視窗。
- 點選某列會有反白提示；表頭在捲動時會固定，方便處理長名單。
- 【問券】可查看該客戶尚未完成的問卷。
- 外撥完成並送出電話小結後，TM 應保留原本的搜尋與標籤篩選結果；若篩選條件消失，先確認小結是否成功，再重新查詢並記錄時間與客代。

## 三、查詢條件、限制與互斥

### 3.1 商品、未曾購買與文字條件

- 【商品】查詢買過指定商品的客戶；【未曾購買】必須搭配【商品】，用來查詢未買過該商品的客戶。商品名稱空白時不會形成有效查詢，先補上商品名稱。
- 【商品名稱】是以客戶曾購買的品名查詢，受系統效能限制，依目前手冊僅查近 2 年。
- 【外撥交談註記／memo】可輸入關鍵字，找出交談註記或電話小結聯繫內容符合的名單；【標籤】可用關鍵字或下拉選項篩選，標籤的實際語意由後端與資料來源決定。
- 【信用卡】可篩選信用卡欄位為「是」的客戶；【買過 84/134】可篩選最後購買 84/134 有值的客戶。這些條件可與其他條件組合，例如「買過 84/134 + 信用卡」。

### 3.2 未撥打、回收與預約外撥

| 條件 | 操作與限制 |
|---|---|
| 【未撥打】 | 可輸入天數，最多 30 天；通話未達 10 秒仍可能被視為未聯，應納入未撥／未聯判讀。第 31 天可能回收名單。 |
| 【回收（30D 未聯）】／【回收（到期未成）】 | 兩者只能擇一。不要同時用兩個回收條件推導結果。 |
| 【預約外撥日期】 | 由電話小結【重新安排】寫入；日期等於系統日才會帶出，可與 `Call now` 及未撥打天數併用。來源手冊記載【重新安排】最多預約三個月內；若現行公告或 UI 不同，以現行規則為準。預約時間前約 30 分鐘會由小鈴鐺提醒。 |
| `Call now` | 顯示目前時間適合撥打的客戶；它是時段條件，不代表已完成電話行銷同意檢查。 |

名單效期與回收的歷史操作描述包括：新分派名單起始效期 90 天；連續 30 天沒有超過 10 秒的有效 TM 外撥，或到達最終效期仍未成交，系統可能回收。歷史手冊記載，成交純 OB 通路商品（前置碼 84/134）於訂單日自動展延 120 天，成交 OB-T 型網商品自動展延 60 天；若判定的展延日期不晚於原效期則維持原效期。這些天數仍應依目前業務規則與電話小結／訂單資料判讀，不要只從列表顏色推算。

### 3.3 LINE、360 與以物搜人

- 【LINE 綁定】可選擇有綁定或沒綁定 LINE，適用一般名單及推薦名單。
- 【360 畫像篩選】可依美容偏好、保健功效等選項找出名單倉內的目標客戶；【以物搜人】使用專門的 MI360 葉節點標籤清單。
- 「無買過自然美美妝」是目前手冊列出的 360 篩選例子。該手冊同時記載排程可能造成約一天的資料時間差，因此篩選結果不可直接當成即時購買事實；遇到當日已購買仍被列入，先確認資料更新時間與當期公告。

### 3.4 客代、生日、等級與人員條件

- 【查詢客代／多客代】最多 100 筆。管理職跨專員查詢時，客代需有維運專員才會納入結果；超過上限請分批，勿把空白結果當成服務故障。
- 【出生日期】可輸入月份或月日片段，例如 `-09-` 查 9 月生日、`-08-02` 查 8 月 2 日生日。格式若不被畫面接受，先依目前欄位提示輸入，不要自行改成未支援格式。
- 【會員等級】依客戶在東森各通路的消費金額；【OB 會員等級】依 OB 通路消費資料。若等級與查詢結果不一致，先確認資料更新時間及所選查詢視角。
- 【舊客】是表示曾在 OB 通路消費（歷史手冊列出 OB-84、新零售-134、OB-T 型網 47/48/49）；【成交客戶】是表示由目前專員本人成交；【追蹤狀態】取最後一次電話小結，`維護` 也可用來找新分派名單。
- 【專員類別】可篩選「全部、1、2、3、4、5、空白」。這是專員在客戶資訊卡設定的個人維運分類，不是被指定人的權限條件。

歷史手冊列出的 OB 等級級距如下，僅作畫面判讀參考；若目前業務公告或系統選項不同，以現行規則為準：

| OB 等級 | 歷史手冊描述 |
|---|---|
| A | 半年 OB 商品累積消費金額至少 60,000 元，且 OB 通路消費至少 3 次。 |
| B | 半年 OB 商品累積消費金額至少 30,000 元，且 OB 通路消費至少 3 次。 |
| C | 半年 OB 商品累積消費金額至少 5,000 元，且 OB 通路消費至少 2 次。 |
| D+ | 半年 OB 商品累積消費金額至少 2,000 元，且 OB 通路消費至少 1 次。 |
| D | 半年內 OB 通路消費至少 1 次，不限金額。 |
| E | 半年內只買過 OB- 商品。 |
| Z | 曾經買過，但半年內未購買 OB 及 OB- 商品的停滯客。 |
| 空白 | 尚未購買 OB 或 OB-T 型網商品的新客。 |

## 四、推薦名單的 11 類標籤

推薦名單是公司建議優先處理的工作集合，不是專員自行建立的永久清單。下表的部分觸發與結案細節來自 `MI完整手冊.md` 的歷史操作段落，現有技術來源沒有重新定義全部業務時點；因此以下均屬「依現行業務公告／來源文件」的操作參考，當期公告或畫面狀態不同時以當期規則為準。

| 推薦標籤 | 觸發情境 | 結案／移除條件 |
|---|---|---|
| 【客訴未結】 | 依現行業務公告／來源文件：IB 建立要求 OB 回電的客訴時產生；歷史手冊舉例，OB 專線超過 20 秒未接可能轉 IB。 | 客訴結案後不再出現在推薦名單；若仍顯示，先回查客訴狀態與同步時間。 |
| 【指定回電】 | 依現行業務公告／來源文件：客戶進線但專員未接通，客戶在 20 秒內掛斷時，系統可能產生指定回電待辦。 | 客戶待辦結案後移除；先依[客服員待辦事項](14-客服員待辦事項.md)核對來源與期限。 |
| 【預約撥號】 | 依現行業務公告／來源文件：電話小結【重新安排】寫入的日期到達當日，即帶出待撥名單。 | 對該客完成外撥後不再出現在推薦名單；若回到列表仍在，先確認小結與外撥紀錄是否完成。 |
| 【到貨未聯】 | 依現行業務公告／來源文件：訂單配送日期後第 2 天產生到貨未聯待辦；歷史手冊記載待辦期限為 14 天，現行期限以公告／來源文件為準；每天每客代通常只出現一筆。 | 成功外撥（排除電敗）或手動結案待辦後，待辦與標籤同步移除；當天電敗可能使名單隔日仍出現。 |
| 【超取未聯】 | 依現行業務公告／來源文件：配送至超商隔日產生標籤與同名待辦。 | 歷史手冊記載滿 7 天或成功外撥後自動結案並移除；若外撥前訂單已變成「配送確認（已取貨）」，可依目前流程手動結案。 |
| 【當月生日壽星】 | 依現行業務公告／來源文件：當月生日且 OB 會員等級 A、B、C；是否貼標視當月壽星活動公告。 | 歷史來源未固定說明單一移除時點；依當月活動公告、標籤同步與相關待辦結束狀態確認，不自行推定。 |
| 【回收（30D 未聯）】 | 依現行業務公告／來源文件：距離上次外撥到第 30 天，當日需聯繫；最後外撥日距今至少 25 天時，歷史手冊記載可能反綠提醒。 | 當日完成有效 TM 外撥後通常不再列於推薦；通話未達 10 秒仍可能被視為未聯，隔日可能回收。 |
| 【回收（到期未成）】 | 依現行業務公告／來源文件：名單今日到期且效期內未成交 OB／OB-T 型網商品；效期剩 5 天內，歷史手冊記載可能反紅提醒。 | 當日成交後不再列於推薦；若到期日仍未成交，歷史手冊記載隔日回收。 |
| 【3 天內美容預約】 | 依現行業務公告／來源文件：有 Regal 美容預約，距到店日前 3 天加入推薦提示。 | 外撥提醒後至客戶儀表板結案待辦；超過預約日期，歷史手冊記載標籤會自動結案。 |
| 【3 天內健康預約】 | 依現行業務公告／來源文件：有栢馥健康預約，距到店日前 3 天加入推薦提示。 | 外撥提醒後至客戶儀表板結案待辦；超過預約日期，歷史手冊記載標籤會自動結案。 |
| 【新分派】 | 依現行業務公告／來源文件：系統當日自動分派名單。 | 當日應完成外撥；歷史手冊記載若當日未撥，隔日回收。推薦標籤本身的即時移除時點若與畫面不同，依當期公告及名單狀態確認。 |

處理推薦標籤後，不要只看小鈴鐺是否消失；回查原客代的待辦、客訴、電話小結與名單標籤是否同步。通知只是入口，並不代表案件已結案。

## 五、欄位顯示與列表操作

1. 點【欄位顯示設定】自訂列表欄位。歷史手冊記載預設全選、預設顯示 18 項；畫面若有差異，以目前欄位設定為準。
2. 下列欄位不可移除：**已撥、客戶編號、有效日、姓名、身分別、OB 會員等級**。
3. 【已撥】表示今日已由維運專員完成 TM 外撥；非維運專員外撥不會以此方式計入。
4. 客戶編號欄位可快速查詢，也可清空欄位過濾器；過濾標籤提供【全部】選項。
5. 外撥後小結完成應保留目前搜尋與標籤結果。若要確認是否真的更新，先回查該列的已撥、追蹤狀態、有效日與推薦標籤。

## 六、點客代後的客戶側邊視窗

側邊視窗採延遲載入，不會一次載入所有分頁。首次開啟時從第一個分頁開始；視窗已開啟時切換其他客戶，會保留目前正在看的分頁。視窗沒有遮罩，仍可在開啟狀態下點另一位客戶。

### 6.1 固定載入與分頁

點客戶姓名開啟側邊視窗後，先看固定顯示的會員儀表板、客戶優惠與未完成待辦；訂單分頁需要的通路選項也會準備好。既有分頁的其他資料在切換到對應分頁時載入；AI 分頁的實際讀取方式以當期畫面與維運查核為準。畫面上的資料未出現時先重開該分頁，不要直接判定整頁故障。

以下保留八個分頁；各分頁的實際可見內容仍以目前 UI、權限與功能設定為準。

| 分頁 | 內容與使用方式 |
|---|---|
| 訂單清單 | 查看客戶訂單、商品銷售編號與商品明細；需要時點商品銷售編號進一步查看明細。 |
| 外撥交談註記 | 在同一列表查看通話紀錄與電話小結／交談註記，並可用關鍵字找聯繫內容或新增聯繫描述。 |
| 消費輪廓（SCV） | 查看累計、近一年／近三年消費、通路偏好、商品分類及通常聯繫時段等資訊。 |
| 客戶備註 | 查看客戶常態性資訊，例如方便聯繫時間；若權限允許，可新增或修改備註。 |
| 360 畫像 | 查看消費、美容／保健偏好、寵物等標籤；若畫面提供，可留下目前專員的讚／倒讚回饋。 |
| 人物誌 | 查看另一份外部產出的客戶標籤、消費概況與人物摘要；沒有資料時不代表 360 分頁故障。 |
| 專員類別 | 查看目前專員對客戶設定的 1～5 或空白分類；修改後依畫面再次確認。 |
| AI 穿雲箭 | 查看與客戶相關的銷售商品；符合【以物搜人】商品條件時會有提醒圖示。選商品後可使用推薦話術、拒應話術、對話與對話記錄；細節依當期畫面與公告。 |

若只切換客戶而沒有關閉側邊視窗，畫面會沿用當下正在看的分頁；首次開啟則從第一個分頁開始。各分頁的資料判讀、寫入結果與異常處理見 6.2～6.5。

### 6.2 AI 穿雲箭（Redmine #49910「AI銷售總指揮」）

「AI 穿雲箭」是目前業務稱呼；Redmine 主單名稱為「AI銷售總指揮」。Redmine 與既有技術解析是功能設計與來源整理，並不代表每個細節都已在目前環境實機確認；若當期 UI、公告或系統回應不同，以當期資訊為準。

#### 操作流程

1. 在客戶側邊視窗開啟【AI 穿雲箭】分頁，先看是否有可處理的相關銷售商品。商品來源對應【以物搜人】的商品標籤；符合相關條件時會顯示提醒圖示。
2. 選擇商品後，查看【對話啟動器】、【推薦話術】、【拒應啟動器】、【對話框】與【對話記錄】。點選商品啟動器後，畫面應顯示對應回覆；啟動器內容與商品對應以當期畫面設定為準。
3. 查看【對話記錄】時，主單／子單描述的判讀範圍是同一客戶、同一商品近 90 天的對話，並應能辨識專員姓名與日期；來源未確認的欄位與實際範圍，以當期畫面與系統回應為準。
4. 客戶資訊卡未關閉、只切換同一張卡片內的分頁時，不建立新的對話。來源只確認這個同卡切換邊界，沒有證明切換客戶或商品時的對話上下文規則，不要延伸推定跨客戶或跨商品共用對話。

#### 正常結果與先檢查什麼

| 畫面結果 | 先檢查 | 判讀方向 |
|---|---|---|
| 商品清單為空 | 客戶是否有相關商品、【以物搜人】商品條件與當期功能是否啟用。 | 可能是沒有符合商品或目前設定尚未提供資料，不要只因 AI 分頁空白就判定 TM 名單整頁故障。 |
| 選商品後沒有話術或按鈕 | 是否真的選到商品、畫面是否完成載入、當期商品設定是否有內容。 | 先區分沒有設定與載入失敗；未實機確認的畫面呈現以當期回應為準。 |
| 對話沒有回覆或記錄沒有更新 | 記錄客代、商品、時間與畫面提示，區分「沒有得到回答」和「回答已顯示但記錄未寫入」。 | 兩者是不同異常，交由維運依 9.2 的查核對照處理。 |
| 對話記錄空白 | 客戶、商品、查詢範圍與是否確實有歷史對話。 | 可能是沒有符合範圍的歷史資料；不要把空集合直接視為服務錯誤。 |

### 6.3 儀表板與資料判讀

#### 操作流程

1. 開啟客戶側邊視窗後，先在儀表板確認客代、姓名、電話、生日、付款偏好、維運專員、建議時段、LINE 綁定與 OB 會員等級，再搭配優惠與待辦判斷下一步。
2. 到【訂單清單】確認曾消費的商品；銷退中的訂單與已完成銷退會有不同標示，需要細節時點商品銷售編號查看明細。
3. 到【客戶待辦】處理尚未完成的項目；新增時填妥【待辦描述】、【提醒時間】與【到期時間】，結案時填寫完成內容。新增或結案後，以畫面結果重新確認，不要只看送出按鈕是否關閉。
4. 查看【客戶備註】時，可依目前可用的權限查詢或修改既有內容；新增備註要先通過欄位與內容檢查。查詢／修改的權限判斷，與新增時的欄位驗證是兩件事，不要互相推定。
5. 【專員類別】可設定 1、2、3、4、5 或空白，作為目前專員的維運分類；按下確認後依畫面再次確認是否真的修改。

#### 正常結果與資料判讀

- 儀表板、優惠與待辦是開啟客戶卡時的基本工作資訊；待辦區只顯示未完成項目，完成的待辦不會繼續列出。
- 【消費輪廓（SCV）】可查看累計、近一年／近三年消費、通路偏好、商品分類與通常聯繫時段，適合用來安排聯繫時機與了解消費背景。
- 360 標籤旁的讚／倒讚是目前專員的回饋，不等於客戶已確認的事實；回饋儲存成功後才算留下操作紀錄。
- 待辦建立、待辦結案、備註新增／修改與專員類別修改都是寫入操作；畫面出現失敗或沒有更新時，先保留輸入內容、客代與時間，再重新查詢確認。

#### 異常先判斷

- 儀表板、優惠與待辦全部空白時，先記錄客代、時間與畫面提示；只有單一資料區塊空白時，先按單一分頁或資料來源排查，不要直接升級成整個客戶卡故障。
- 待辦、備註或專員類別送出後沒有更新，先確認欄位檢查、目前權限與是否收到失敗訊息，再重新查詢；不要把送出動作本身當成寫入成功。

### 6.4 外撥交談註記的資料合併與寫入邊界

#### 從哪裡進入與會看到什麼

在客戶側邊視窗開啟【外撥交談註記】。這個列表會把兩類資料整理在一起：

1. **通話紀錄**：聯繫日期、通話時間、建立人員與日期等外撥資訊。
2. **電話小結／交談註記**：電話小結內容與專員補充的聯繫描述。

因此，列表顯示的是合併後的客戶聯繫脈絡；電話小結的聯繫內容也會納入關鍵字查找。列表筆數與名單上的【外撥交談註記／memo】篩選結果用途不同，不能直接拿筆數互相比較。

#### 新增註記與正常結果

1. 在列表中輸入必要的聯繫描述；可以新增沒有關聯電話的聯繫描述。
2. 按送出後，先看畫面是否回報成功，再重新查看列表或以客代確認結果。只有視窗關閉、畫面暫時顯示文字，不能單獨當成已寫入。
3. 只記錄完成工作所需的聯繫內容，不要在交談註記記錄病史、政治立場或個人負面觀感。

新增失敗時，先保留畫面訊息、客代、輸入內容與時間；修正欄位或排除服務問題後再重送，不要把失敗當成已完成的電話小結。

#### 空白、筆數不同與部分資料

- 側邊視窗列表空白，先確認客代、分頁與重新載入時間，區分「客戶沒有資料」「合併後沒有資料」和「系統回報錯誤」。
- 名單篩選查不到客代時，先按「沒有符合關鍵字」判讀；它不表示側邊視窗一定沒有通話紀錄，也不表示兩邊資料必須有相同筆數。
- 若列表看起來只少了通話紀錄或只少了電話小結，現有來源沒有定義單一來源失敗時是否回傳部分結果；需交由維運依 9.3 查核，不能只看空白畫面推論整個側邊視窗故障。

### 6.5 360 畫像與人物誌資料判讀

#### 360 畫像：標籤資料與專員回饋

1. 進入【360 畫像】查看客戶的消費、美容／保健偏好、寵物等標籤與分類結果。
2. 標籤是多來源畫像資料的呈現；若畫面提供【讚】或【倒讚】，那是目前專員對標籤的回饋，不是客戶已確認的事實。
3. 回饋送出後，以畫面結果或重新載入確認是否成功；失敗時不能當成已完成，也不應把回饋結果寫成客戶本人的陳述。

360 可能只顯示部分標籤。遇到空白或缺項時，先重新開啟分頁並確認該客戶是否有相應標籤；標籤節點缺少時可能只影響部分明細，不能直接推論整個側邊視窗故障。

#### 人物誌：獨立的外部客戶摘要

1. 進入【人物誌】查看另一份外部產出的客戶摘要，例如標籤、消費概況與人物摘要。
2. 人物誌與 360 是獨立資料來源；人物誌沒有資料或顯示空值，不代表 360 沒有標籤，也不能用 360 內容代替人物誌。
3. 若畫面提供人物誌標籤回饋，先通過欄位與業務檢查，再以目前登入者留下回饋；目前來源沒有確認這兩個回饋入口的傳輸細節，依當期 UI／回應為準。

#### 先判斷哪一個分頁有問題

- 360 空白／部分缺項：先確認是否只是沒有標籤或某個標籤節點缺失，再確認回饋狀態是否只是查無目前專員資料。
- 人物誌空白／空值：先按外部資料沒有結果判讀，再區分服務錯誤或逾時；不要把空值當成 360 故障。
- 兩個分頁同時或分別異常：分別記錄客代、分頁、時間與畫面回應。單一分頁無資料不等於名單、儀表板或另一個分頁故障。

## 七、外撥守門與外撥後銜接

### 7.1 撥打前

1. 只從 TM 列表的電話圖示開始撥打，選擇客戶電話後按【撥打】。不要用桌上話機，或直接在軟體電話輸入號碼；這些方式不會列入 TM 名單外撥紀錄。
2. 確認軟體電話已開啟且登入時有分機。未填分機時，列表可能隱藏電話圖示；未開軟體電話直接點圖示也不會建立聯繫記錄。
3. 系統會先檢查客戶是否接受電話行銷。回傳「否」時應停止外撥，畫面會提示警語並將名單狀態更新為「1202 不接受外呼」；查無客代時也會直接中止，不要把守門失敗當成一般空名單。
4. 客戶姓名或外撥跳轉客戶查詢時可能出現客戶分群／勿推提醒。依畫面警示與目前業務規範處理，不要跳過警示直接推廣。

### 7.2 通話後

- 非該名單維運專員的外撥不列入 TM 計算，例如不會用來消除 30 天未聯條件。
- 通話結束要完成電話小結；小結完成後 TM 名單會更新。通話未達 10 秒仍可能被視為未聯，所以不能只以「曾按過撥打」判斷已完成有效聯繫。
- 若客戶要求稍後再聯繫，在電話小結使用【重新安排】；來源手冊記載最多預約三個月內，若現行公告或 UI 不同，以現行規則為準。送出後回 TM 以【預約外撥日期】查詢。預約資料與小鈴鐺通知、名單回收及維運專員變更有連動，若名單回收造成預約人員與現任維運專員不一致，預約資料可能被清除。
- 小鈴鐺可能通知指定回電、客訴未結、預約外撥或其他工作事件。通知消失不代表待辦已結案，仍要回原功能確認待辦、客訴、電話小結與名單狀態。

## 八、常見異常與判斷順序

| 現象 | 先檢查 | 判斷方向與處理 |
|---|---|---|
| 查無一般名單 | 被指定人、權限、所有篩選條件、客代是否有維運專員。先按【清空】再用最小條件查詢。 | 可能是查詢視角或條件沒有命中；查無資料本身可以是正常結果。若最小條件仍完全無資料，再提供帳號角色、客代／條件與時間給維運判斷資料同步或服務異常。 |
| 推薦名單空白 | 今天是否有符合 11 類推薦情境、30D／到期條件是否二選一選錯、目前被指定人是否正確。 | 優先判斷為條件未命中或當日沒有推薦資料，不要直接視為頁面故障；若同一視角在公告所述條件明確成立仍空白，再查推薦資料或排程狀態。 |
| 側邊視窗只有部分分頁空白 | 先切回固定儀表板，再逐一重開空白分頁；記錄客代、分頁與發生時間。 | 側邊視窗採分頁載入，單一分頁沒有資料或載入失敗時，先保留名單與其他分頁的判斷。若只有 SCV／人物誌空白，先查各自資料來源；若固定儀表板也失敗，才提高為服務或客戶資料組裝問題。 |
| 預約外撥未出現 | 電話小結是否成功送出【重新安排】、預約日期是否為今天、是否超出目前允許範圍（來源手冊記載最多三個月；現行公告／UI 優先）、名單是否已回收或維運專員已變更。 | 先排除日期、三個月預約上限與名單狀態條件；再回查待辦與小鈴鐺。若現行公告／UI 所示條件都正確仍沒有，再判斷資料同步或通知服務延遲。 |
| 外撥後結果消失 | 是否從 TM 電話圖示撥打、軟體電話是否開啟、是否完成小結、通話是否未達 10 秒，以及目前看的是一般名單還是推薦名單。 | 推薦標籤因完成外撥／結案而消失可能是預期狀態；一般名單的原查詢與標籤篩選應保留。若小結成功但應保留的結果消失，記錄客代與篩選條件，區分畫面刷新、寫入同步或服務異常。 |
| 被指定人查不到資料 | 目前帳號角色是否可切換、被指定人是否真的有分派資料、查詢客代是否超過 100 筆或缺少維運專員。 | 一般專員不能以切換被指定人擴大範圍；目前來源只確認 `Admin` 可切換查詢視角，主管／管理職／名單管理權限仍須對照目前授權矩陣與 UI。先處理權限問題與條件未命中，最後才升級資料或服務異常。 |
| 商品／標籤／memo 查詢報錯 | 商品是否空白、標籤與值是否可選、memo 是否有關鍵字。 | 商品空白是可預期的輸入錯誤；其餘條件可能是沒有命中或資料來源異常。若相同有效條件在不同時間反覆失敗，提供條件、角色、時間與畫面訊息，交由維運查詢。 |
| 外撥交談註記顯示與名單篩選結果不同 | 先分辨是在看側邊視窗的合併列表，還是在名單上用 memo 關鍵字篩選；再核對客代、關鍵字、查詢視角與時間。 | 兩者用途與資料整理方式不同，不能直接比較筆數或把一方空白判定為另一方故障；回到本文件 6.4，分開查核兩類資料與是否只是沒有命中。 |
| 360／人物誌分頁空白或資料不同 | 分別重開兩個分頁，確認客代、時間與畫面結果；360 另看標籤是否存在，人物誌另看是否只是沒有外部資料。 | 360 的標籤與專員回饋、人物誌的外部客戶摘要是不同資料鏈；人物誌空值不等於 360 故障，單一分頁空白也不等於整個側邊視窗失效。 |
| AI 穿雲箭分頁空白／對話失敗 | 先確認商品、提醒圖示、話術、對話與記錄的哪一段沒有結果，並保留客代、商品、時間與畫面提示。 | 先區分沒有符合商品／話術、AI 沒有回覆、串流中斷與回答已顯示但記錄未寫入；AI 分頁或單一對話失敗不應直接判定 TM 名單、既有側邊視窗或其他分頁整體失效。 |

排查時至少保留：登入角色、被指定人、客代（必要時遮罩）、查詢條件、推薦標籤／待辦名稱、發生時間、是否使用 TM 電話圖示、電話小結與小鈴鐺狀態。不要在一般文件或通報中貼出帳密、Token 或不必要的個資。

## 九、維運查核補充（短版）

本節只在畫面結果不足以判斷時使用。先依前文完成操作與記錄，再用客代、查詢視角、時間及畫面結果對照 action、資料來源與 log；來源未確認的 runtime 行為仍以當期 UI、公告、回應與設定為準。

### 9.1 名單與側邊視窗對照

| 畫面用途 | endpoint／action | 維運判讀重點 |
|---|---|---|
| 一般名單／推薦名單 | `GET /api/OutBoundTMList/GetTmList`、`GET /api/OutBoundTMList/GetRecommendData` | `Admin` 可透過 `userId` 切換查詢視角；查無資料可回空集合，不先當成錯誤。 |
| 商品、標籤、memo 篩選 | `POST /api/OutBoundTMList/GetCustomerIdByProduct`、`GetCustomerByTag`、`GetCustomerIdByMemo` | 商品空白會是 `BadRequest`；memo 篩選由 `FUGO21.SPX_OB_GETCUSTLISTBYTMMEMO` 回傳客代集合，不等於側邊視窗 note 列表。 |
| 切換客戶時固定準備 | `QueryCustomerDashboardInfo`、`GetCustomerDiscount`、`GetCustomerTodo`、`QuerySubChannelOptions` | 儀表板、優惠、待辦與訂單通路選項是固定準備資料；來源設計為既有分頁獨立載入，AI 分頁以當期 UI／API 為準。 |
| 訂單清單 | `POST /api/OutBoundTMList/SearchCustomerOrderInfos` | 查詢與排序訂單，必要時再看商品明細。 |
| 外撥交談註記 | `GET /api/OutBoundTMList/GetCustomerContactNote` | 由 contacts 與 TM memo 組成單一客戶列表；詳見 9.3。 |
| 消費輪廓（SCV） | `GET /api/OutBoundTMList/GetCustomerScv` | 由多個消費與偏好來源組合。 |
| 客戶備註 | `GET /api/OutBoundTMList/QueryComment` | 查詢帶入目前 `access level`；新增／修改是不同的驗證與寫入流程。 |
| 360 畫像 | `GET /api/OutBoundTMList/GetCustomerPortrayTagDetail` | 標籤明細與目前專員回饋狀態組合顯示。 |
| 人物誌 | `GET /api/OutBoundTMList/QueryCustomerBasicInfo` | 外部 BigData 回傳 `null` 時，人物誌可有 `null` payload；不要拿 360 結果補代。 |
| 專員類別 | 無分頁讀取 endpoint，使用本地已載入資料 | 修改另走建立／更新寫入 action，操作者由後端處理。 |

側邊視窗決策文件記載分頁切換用延遲載入；分頁呼叫失敗由前端捕捉並記錄 `console.error`，設計上不應連帶清除其他分頁或固定資料。這是來源描述，實際畫面保留哪些區塊仍以目前 UI 驗證。

### 9.2 AI 穿雲箭 action、歷史記錄與 cache

Redmine 對照：主單 [#49910 AI銷售總指揮](https://redmine.etzone.net/issues/49910)；子單 [#49917 UI](https://redmine.etzone.net/issues/49917)、[#49918 送出訊息 API](https://redmine.etzone.net/issues/49918)、[#49923 Init Data API](https://redmine.etzone.net/issues/49923)、[#49944 對話紀錄 UI](https://redmine.etzone.net/issues/49944)、[#49947 對話紀錄 API](https://redmine.etzone.net/issues/49947)、[#49949 Cache](https://redmine.etzone.net/issues/49949)、[#49950 streaming PoC](https://redmine.etzone.net/issues/49950)。Redmine 與 SaleBot L1／log-map 是設計與技術解析來源，不能代替目前 runtime 證據。

商品提醒圖示的來源對照為 Redmine 主單描述的 `tag_class2` 判斷；若當期畫面或資料欄位不同，以當期 UI／回應為準。

| action | 方法／路由 | 維運查核重點 |
|---|---|---|
| `QueryInitData` | `GET /api/SaleBot/QueryInitData` | 讀取啟用的 `SALE_BOT` Domain Data，展開 `TagId`、`TagName`、`DialogueStarter`、`Rejection`、`Sort`；沒有設定時可回空集合。 |
| `Chat` | `POST /api/SaleBot/Chat` | 一般對話使用 `ChatRq`；L1／log-map 列出的 `UserId`、`CustomerId`、`Goods`、`Rule` 是追查線索，不擴寫成未確認的 UI 契約。回應物件為 `null` 時記錄／拋出 `SaleBot response error` 與 `ExceptionCode.SystemError`。 |
| `ChatStream` | `POST /api/SaleBot/ChatStream` | SSE 只把 `delta` 內容轉給前端；使用者中斷的 `OperationCanceledException` 不應當成服務錯誤。其他串流例外會寫失敗紀錄並送出 `error` SSE。 |
| `Log` | `GET /api/SaleBot/Log` | 以 `id`、`tagId`、`count`、`customerid` 查詢並展開 `user`／`assistant` 訊息；沒有歷史時可回空集合。 |

歷史記錄的追查邊界：主單／#49947 描述同客戶同商品近 90 天、每次 20 筆並可向上翻頁；request 的 `id` 是流水號／游標，`tagId` 是商品／標籤代碼，`count` 是每次筆數。response 至少關注 `id`、`message`／`Message`、`role`、`rule`、`sendTime`；專員姓名、90 天過濾、固定 20 筆與游標邊界的目前實際行為，仍須用當期 response／UI 確認。

cache 來源有兩種層級描述：主單記載推薦話術、對話啟動器與拒應啟動器約每日生成一次；[#49949](https://redmine.etzone.net/issues/49949) 的歷史設計則記載商品共用 key 類似 `rediskey:{tagId}_{btnid}`、客戶專屬 key 類似 `rediskey:{customerId}_{tagId}_{btnid}`，快速話術記載 12 小時。TTL、key、清除入口與失效行為以當期設定、公告及實際回應優先，來源沒有證明目前一定有人工清除入口。

AI 異常 log 對照：一般對話答案已回來但成功紀錄寫入失敗，查 `SaleBot 寫入紀錄失敗...`；失敗紀錄也寫不進去，查 `SaleBot 寫入失敗紀錄失敗...`；串流失敗、串流失敗紀錄與串流完成後寫入失敗，分別查 `SaleBot 串流失敗...`、`SaleBot 串流寫入失敗紀錄失敗...`、`SaleBot 串流寫入紀錄失敗...`。不要把記錄寫入失敗與「AI 沒有回覆」合併回報。

### 9.3 資料合併、寫入與操作者邊界

#### 外撥交談註記

- `GetCustomerContactNote` 由 `TmAppService.GetCustomerContactNote(customerId)` 先取 `GetCustomerContacts(customerId)`，再取 `GetCustomerTmMemo(customerId)`，最後由 `BuildContactNotes(...)` 組裝；先放聯繫紀錄，再依 `CallProcessId` 分組 memo。`CallProcessId` 是組裝關聯鍵，不是名單篩選條件。
- `GetCustomerIdByMemo` 是另一個名單篩選入口，依 `memo` 呼叫 `FUGO21.SPX_OB_GETCUSTLISTBYTMMEMO` 回傳符合的客代集合；兩者資料型態、用途與筆數不可互換。
- `POST /api/OutBoundTMList/CreateContactNote` 先映射 `CreateContactNoteCmd` 並通過 request／業務驗證，再由 `CustomerCommandRepository.CreateContactNote(...)` 呼叫 Oracle `SPX_OB_AddTmMemo`。`EmployeeId` 由後端覆寫為目前登入者；SP return code 非 OK 時視為失敗並回 `BadRequest`。
- 來源只確認 TM memo 寫入鏈，沒有保證同步改寫 contacts 或立即出現在下一次顯示查詢；contacts／memo 單一來源失敗、unmatched memo 與 partial failure 的 UI 契約仍是 `runtime 未確認`。

#### 儀表板、待辦與客戶備註

- 新增待辦的 `todoDesc`、`remindDate`、`dueDate` 都是必填；`CreateTodoList` 的 `AssignedTo` 由後端覆寫為目前登入者，資料庫寫入鏈包含 `SPX_OB_TODONEW`。更新待辦使用 `UpdateTodoList`，`DoneBy` 也使用目前登入者；待辦查詢只回未完成項目。
- 備註查詢／修改會帶入目前 `access level`，修改者 `ModifiedBy` 由後端帶入目前登入者；新增備註則先做 request／業務驗證，建立者 `CreatedBy` 由後端帶入目前登入者。來源未確認新增備註必然套用同一個 access-level 控制，兩者不可合併判讀。
- 相關入口為 `QueryComment`、`CreateComment`、`UpdateComment`；新增寫入來源包含 `SPX_INSCUSTOMERREMARK`，修改寫入來源為 `SPX_OB_updcustomerremark`。驗證失敗或寫入失敗不可回報為成功。

#### 360、人物誌與其他寫入

- 360 查詢由 `TMQueryRepository.GetCustomerPortrayTag(customerId, employeeId)` 組合 `GetPortrayTagList()`、`GetCustomerPortrayData(customerId)` 與 `GetTagThumbsAll(customerId, employeeId)`；標籤依第一／第二層分類排序後合併回饋，來源同時涉及 Oracle 與 MariaDB。找不到標籤節點時該筆 path 會略過；`GetTagThumbs` 查無資料的 `0` 代表沒有目前專員回饋。
- `UpsertThumbsUpDown` 由後端補入 `EmployeeId`／`EmployeeName`，先寫回讚／倒讚，成功後才寫操作 log；upsert 失敗不寫 log。這個回饋不會回寫成客戶事實。
- 人物誌 `QueryCustomerBasicInfo` 直接呼叫 `BigDataClient.GetBasicInfo(customerId.ToString())`；BigData 回傳 `null` 時可回 `null` payload。若 UI 提供 `CreateTagFeedback`／`GetTagFeedback`，建立時先驗證並由後端補操作者，查詢鍵為 `customerId + tagName`；兩支 action 的 HTTP method 未由 canonical source 明確定義。L1 的人物誌 SP 名稱在不同段落有 `usp_tag_feedback_update`／`usp_tag_feedback_add` 差異，本手冊不硬化成單一契約。
- 專員類別的建立／更新 action 會由後端以目前登入者處理；外撥前的同意檢查查無客代會中止流程，將名單改為不接受外呼時則依資料庫回傳碼判斷成功與否。
