## 頁面可見操作

目前頁面可確認的操作是：

- 進入頁面後載入年度下拉選單；畫面提供年度選擇與「查詢」按鈕。
- 清單顯示節日名稱、工作日日期、是否為休假日，並可從單筆資料開啟編輯。
- 提供「新增工作日」與「匯入 CSV」按鈕。
- 目前頁面未見刪除按鈕，也未見對應的刪除 API；不要把更新誤當成刪除。
- L1／API 支援 `year` 與可選的 `name` 條件；目前 frontend component 只呈現年度下拉，`name` 是 API 條件而非目前可見的搜尋欄位。

## 維運查核補充

以下 API、stored procedure、交易與 cache 對照只供維運查核；一般讀者先依前文的年度、日期與 CSV 畫面操作。

| 操作 | Method / endpoint | 輸入與輸出 | 主要資料行為 |
|---|---|---|---|
| 年度選單 | `GET /api/WorkingDay/QueryYearOption` | 無需額外查詢參數；回傳 `{ text, value }` 字串年度清單 | 由全部工作日的 `Date.Year` 分組、遞增排序；查詢可使用 `AllWorkingDay` cache |
| 工作日查詢 | `GET /api/WorkingDay/QueryWorkingDays?year={year}&name={name}` | `year` 綁定為整數；`name` 為可選條件；回傳 `{ id, date, name, isHoliday }` 清單 | 由 `usp_working_day_get` 查詢，回傳前依日期遞增排序；此查詢不走 `AllWorkingDay` cache |
| 單筆新增 | `POST /api/WorkingDay/CreateWorkingDay` | JSON：`date`、`name`、`isHoliday` | 驗證後檢查日期重複，再呼叫 `usp_working_day_add`；成功後清除工作日 cache |
| 單筆更新 | `POST /api/WorkingDay/UpdateWorkingDay` | JSON：`id`、`date`、`name`、`isHoliday` | 驗證後排除自己的 `id` 檢查日期重複，再呼叫 `usp_working_day_update`；成功後清除工作日 cache |
| CSV 匯入 | `POST /api/WorkingDay/UploadFile` | `multipart/form-data`，檔案欄位名稱為 `file` | 解析 CSV、驗證與過濾既有日期後批次新增；成功寫入後清除工作日 cache |

## 年度選單與工作日查詢

1. `QueryYearOption` 取全部工作日資料，以 `Date.Year` 分組並依年度遞增；同年度只產生一個選項。沒有資料時回傳空集合，不是錯誤。
2. 以年度查詢 `QueryWorkingDays`。`year` 是 API 的主要條件，`name` 是可選的輔助條件；結果以 `Date` 遞增排序。
3. 回傳欄位為 `Id`、`Date`、`Name`、`IsHoliday`；前端顯示日期、名稱與休假勾選狀態。查不到資料時回傳空集合。

年度選單查詢的全部資料快取鍵是 `RedisConfig.CacheKey.WorkingDay.AllWorkingDay`。本批限定來源未確認該 cache 的 TTL 與實際部署值。

## 單筆新增與更新

### 新增

1. 在頁面開啟「新增工作日」，填入日期、節日名稱與是否為假日後送出。
2. `Date` 不能是空值；驗證失敗訊息為 `請輸入工作日日期`。
3. 系統先讀取全部工作日，以日期的年月日檢查重複；同日期已存在時回 `BadRequest`，訊息為 `工作日已存在`。
4. 日期會在寫入前取 `.Date`，只保留年月日；成功呼叫 `usp_working_day_add` 後清除 `AllWorkingDay` cache。

### 更新

1. 從清單單筆開啟編輯，送出 `id`、日期、名稱與假日值。
2. 日期不能是空值；驗證失敗訊息同樣為 `請輸入工作日日期`。
3. 系統以日期的年月日查詢既有資料並排除目前 `id`；若其他資料已占用該日期，回 `BadRequest`，訊息格式為 `{yyyy-MM-dd} 工作日已存在`。
4. 更新前也會把日期正規化為只保留年月日；成功呼叫 `usp_working_day_update` 後清除 `AllWorkingDay` cache。

### 欄位與日期規則

| 欄位 | 意義與已證實規則 |
|---|---|
| `id` | 唯一值；查詢回傳，更新時必須提供；新增不需要由操作人提供有效 ID。 |
| `date` | 工作日日期；新增／更新驗證必填，重複檢查以年月日比較，寫入前去除時間部分。 |
| `name` | 節日或工作日名稱；名稱欄位的長度、格式與必填業務規則，已讀來源未確認。 |
| `isHoliday` | Boolean 是否為假日；前端以勾選狀態送出。 |

目前單筆來源只明確驗證日期必填；名稱長度、空白名稱、未來／過去日期限制，以及 `isHoliday` 與日期的業務相容性，均沒有在已讀來源中定義。

## CSV 上傳

前端選擇檔案後以 `multipart/form-data` 的 `file` 欄位送至 `UploadFile`。後端先驗證 UTF-8，再以每行 `Split(',')` 解析；第一列固定視為 header 並跳過。目前可依來源確認的欄位契約如下：

| 欄位 index | 內容 | 寫入規則 |
---:|---|---|
| `0` | 西元日期 | 以 `yyyyMMdd` 解析為日期；解析後以日期的年月日處理。 |
| `1` | 星期 | 只保留在檔案中供人閱讀，不寫入 `WorkingDay`。 |
| `2` | 是否放假 | 來源以字串 `2` 表示假日；其他值的正式合法性與映射行為未由本批限定來源定義。 |
| `3` | 備註／名稱 | 直接寫入 `Name`。 |

空檔案（檔案不存在或長度為 0）直接回傳失敗訊息 `無新工作日`；非 UTF-8 會回 `BadRequest`，訊息為 `上傳的檔案編碼格式必須是 UTF-8。`。只有 header 而沒有資料列時的 validator 回應，需依實際版本確認。

### 重複、批次與交易

- 批次匯入前會讀取既有工作日，以日期的年月日排除已存在資料；全部已存在時回傳成功狀態與 `工作日都存在，不再新增`，不執行寫入。
- 同一檔案中被排除的既有日期會累積重複資訊；實際提示文字與新增筆數訊息依 API 回應為準。
- 批次寫入由 `TransactionScope` 包住；本批限定來源只確認以交易式批次處理，例外對外回應與提交細節需依實際版本確認。
- 單筆新增與更新的交易行為，本批來源未定義；只能確認各自呼叫資料庫寫入後清除 cache，不延伸推論 stored procedure 內部是否另有交易。
- 新增、更新、批次成功寫入後都清除 `RedisConfig.CacheKey.WorkingDay.AllWorkingDay`；查詢年度下一次會重新取得完整資料。清 cache 失敗時的補償或重試策略，來源未定義。

## 錯誤與未定義邊界

### 已確認的錯誤或空結果

| 情境 | 已確認行為 |
|---|---|
| 年度或工作日查無資料 | 回傳空集合。 |
| 新增／更新日期空白 | `BadRequest`；`請輸入工作日日期`。 |
| 新增日期重複 | `BadRequest`；`工作日已存在`。 |
| 更新日期與其他 ID 重複 | `BadRequest`；`{yyyy-MM-dd} 工作日已存在`。 |
| 上傳檔案為空 | `ApiResponse` 失敗；`無新工作日`。 |
| 上傳不是 UTF-8 | `BadRequest`；`上傳的檔案編碼格式必須是 UTF-8。`。 |
| 匯入資料全部已存在 | 成功狀態；`工作日都存在，不再新增`，不寫入。 |

### 目前沒有足夠來源定義的邊界

- 實際角色／權限碼、管理職與一般使用者的差異，以及 API 未授權時的回應。
- CSV 檔名、副檔名、大小、列數上限、空白列、只有 header、欄位不足、額外欄位、錯誤日期、重複日期出現在同一檔案時的正式提示與整批行為。
- `Split(',')` 對引號包住的逗號、換行欄位或其他完整 CSV 語法的支援；不可把它當成已確認支援的 CSV parser。
- 名稱的長度／字元規則、日期可接受範圍、假日值除 `2`／`0` 外的合法性，以及前端日期時區轉換細節。
- 單筆 stored procedure 的內部交易、資料庫唯一鍵錯誤的對外訊息、cache TTL 的實際環境值，以及寫入成功但清 cache 失敗的復原策略。
- `WorkingDayController` 與相關 use case 的 log-map 已確認沒有 `WriteNormalLog`；這不等同於已確認沒有其他平台層級稽核或存取記錄。

遇到上述情境時，先保留原始檔案、請求時間、帳號、API 回應與資料庫錯誤，再交由開發／維運依實際版本確認；不要用本文件補猜行為。
