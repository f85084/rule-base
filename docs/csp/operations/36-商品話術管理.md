# 商品話術管理

本頁對應 `/SalesPitch`，位於「內部工作管理」，用來維護商品話術主檔與銷售編號的綁定。[商品話術管理需求](../requirements/pages/36-商品話術管理.md) 目前為 0 筆需求單；下列操作只依現有 SalesPitch API、頁面流程與既有手冊整理。

## 入口與權限

- 網站路由：`/SalesPitch`；可由 [website-menus.json](../../../data/sources/csp/website-menus.json) 的 `id: 103` 核對，選單分類為「內部工作管理」。
- log-map 只確認登入後可查詢、檢查與操作；沒有提供管理職／一般職的細分矩陣。按鈕是否顯示以帳號實際授權為準，新增、更新、刪除前應確認目前登入者。
- 新增與更新會以登入者覆寫 `CreatedBy`／`ModifiedBy`；刪除會以登入者帶入 `ModifiedBy`，不要把請求 body 中的操作者欄位當成可信來源。

## 列表與商品名稱查詢

`POST /api/SalesPitch/GetList` 接受 `SalesPitchListRq`，提供話術列表與分頁資料。來源明確描述兩條查詢路徑：

- 有 `ProductName` 時，先走 Vespa 商品名稱搜尋，取得符合商品的銷售編號，再透過話術綁定查詢與話術 ID 展開列表；這不是直接以商品名稱查 MariaDB。
- 沒有 `ProductName` 時，直接以 `SaleNo` 查話術列表；列表資料來自 `usp_salesPitch_getList_v1`。
- 每筆結果會再補 `CreatedName`、`ModifiedName` 與商品名稱；`Total` 取列表第一筆資料的總筆數，列表為空時 `total` 為 0。
- `SaleNo` 與 `ProductName` 是來源描述的兩條互斥查詢入口；Vespa 的關鍵字匹配、排序與實際分頁細節沒有在 Controller 中展開，不要自行承諾模糊比對規則。

在列表點選銷售編號時，頁面另可透過共用商品查詢 API 開啟商品明細彈窗；那是 `Common` 查詢，不是 SalesPitch controller 的新增功能。商品名稱查詢失敗時，先保留原始條件、帳號與回應，不要以空列表推論話術已被刪除。

## 話術模板與明細

| 操作 | API | 來源可確認的行為 |
|---|---|---|
| 載入話術模板 | `POST /api/SalesPitch/GetSalesPitchItem` | 讀取 `MoneyInDomainData.SALES_PITCH` 的 JSON，解析成 `SalesPitchItem` 清單，供新增／更新表單勾選可編輯項目。 |
| 載入明細 | `POST /api/SalesPitch/GetSalesPitchById` | 以 `pitchId` 取得話術主檔，並將 Domain 模板與內容組成前端明細。 |

MI 手冊列出 OB 話術常見的「商品亮點、開場白、產品重點、價格優惠、案例短篇、成交核對」欄位；管理頁實際模板來自 `SALES_PITCH` DomainData，應以當下 API 回傳的項目為準，不要將手冊中的示例欄位或固定數量當成不可變的資料表規格。

明細組裝需要模板與話術內容兩邊都存在；任一邊為空會回失敗結果。`SalesPitchDetail` 若不是可解析的 JSON，來源沒有提供 fallback，應保留原始 `pitchId`、回應與時間交由維運確認。

## 新增話術

1. 開啟新增表單，先由 `GetSalesPitchItem` 載入目前模板。
2. 填入話術內容與銷售編號清單；送出前會先執行 `SendCheck`，驗證模板內容與每筆銷售編號。
3. `ValidateTemplates` 不接受空白／未完成的話術項目；每筆銷售編號會檢查是否已綁定話術及是否能查到商品。
4. 驗證通過後，`AddSalesPitch` 先寫入話術主檔，再寫入銷售編號關聯。任一銷售編號已設定、查不到商品或檢查失敗時，回 `InvalidArgument`／`BadRequest` 類型的失敗，不要略過檢查直接重送。

API：`POST /api/SalesPitch/AddSalesPitch`。新增主檔與銷售編號關聯是兩段式流程；部分關聯寫入失敗後的補救方式未在 Controller 文件中定義，需保留失敗項目與回應交由後續確認。

## 更新話術

`POST /api/SalesPitch/UpdateSalesPitch` 先驗證新模板與新增銷售編號，再更新話術主檔，最後同步維護銷售編號關聯：

- 新增的編號寫入 `usp_salesPitch_addSaleNo_v1`。
- 被移除的編號透過 `usp_salesPitch_deleteBySaleNo_v1` 刪除關聯。
- 未變更的編號也會進入更新流程的分類；來源指出相關處理會清理快取。
- 主檔更新失敗會回「商品話術更新失敗」類型結果；刪除關聯失敗會累計在回應訊息，不一定中止整個更新。
- `ValidateSaleNoList` 可接受 `null`，代表某些更新只改模板、不調整銷售編號；不要把空清單與 null 自行解讀成相同業務意義。

更新成功後會清除以話術 ID 及相關銷售編號為範圍的話術快取，讓下一次查詢重新取得資料。

## 刪除話術

`POST /api/SalesPitch/DeleteSalesPitch` 只以有效整數 `id` 指定話術，後端由登入者補 `ModifiedBy`，執行 `usp_salesPitch_delete` 後回傳成功／失敗結果。話術不存在或刪除失敗時可能只回失敗，不會在 Controller 展開細節；快取清除由 use case／repository 下層處理，不能用前端列表消失推論所有關聯快取都已更新。

## 銷售編號檢查、快取與例外

`POST /api/SalesPitch/CheckSaleNo` 的流程是先查話術綁定，再在需要時查商品名稱：

1. 以 `saleNo` 查話術綁定的快取／資料庫；已存在時回 `IsExist = true`。
2. 未存在時呼叫共用商品查詢取得 `ProductName`，供表單顯示與後續綁定。
3. 銷售編號無效、已設定過、找不到商品或檢查資料為空時，依來源回 `BadRequest` 類型結果；銷售編號需先通過數字／有效輸入檢查。

Repository 查既有綁定若發生例外，來源描述為吞掉例外並回 null，再繼續商品名稱查詢；這不代表所有商品查詢例外都會被吞掉。新增／更新／刪除屬資料異動，查詢列表、模板、明細與檢查本身不寫入資料；目前文件沒有提供快取 key、TTL 或人工清快取按鈕，不要自行補上。
