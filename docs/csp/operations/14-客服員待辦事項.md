# 客服員待辦事項

## 1. 用途、入口與路由差異

本頁集中查看目前客服人員的客戶待辦，可依指定日期、待辦來源、訂單／客訴關聯與處理狀態追蹤後續工作。需求頁標示 route `/OutBoundTodoList`；目前前端 `routes.ts` 的實際 route 字串為 `/OutboundTodoList`，大小寫差異應以當期選單與 runtime 導向結果為準（**runtime 未確認**）。

待辦資料是針對客服人員的紀錄，已處理與未處理皆可能呈現。一般客服先處理自己的待辦；「顯示所有待辦事項」及修改權限是否依角色限制，來源尚未提供完整矩陣，應以當期 UI／後端授權為準。

## 2. 正常操作流程

1. 從小鈴鐺或功能選單進入客服待辦清單。
2. 預設查詢目前客服人員的待辦；需要時勾選【顯示所有待辦事項】，再按【查詢】。
3. 依指定日期排序，核對客代、待辦描述、來源、期限、狀態及關聯訂單／客訴。
4. 打開待辦關聯作業，完成指定回電、到貨未聯、超取未聯、客訴或其他服務事件。
5. 依事件規則完成外撥結案或手動結案，回查清單確認狀態與筆數已更新。

## 3. 欄位與資料來源

- 待辦來源可能包含指定回電、到貨未聯、超取未聯、客訴與其他客戶服務事件；來源名稱是導向後續作業的線索，不是完成結果。
- 清單目前以分頁資料呈現，需同時確認目前頁碼、每頁筆數與總筆數；切換頁碼會依原條件重查。
- 主要判讀欄位為客代、待辦描述、指定／提醒日期、期限日期、狀態、訂單編號、訂單項次與客訴編號；欄位是否顯示以當期清單為準。
- 「顯示所有待辦事項」會改變查詢範圍；勾選與未勾選的空結果不可直接互相比較。

**現行事實**：目前前端會以 `isAll`、頁碼與每頁筆數查詢待辦列表；清單與更新待辦是不同請求。客代是後續服務上下文的主要鍵，待辦識別值是狀態更新的主要鍵。

## 4. 寫入與跨頁副作用

- 查詢是唯讀；勾選【顯示所有待辦事項】只改變查詢範圍。
- 待辦處理或結案會更新待辦狀態，並可能影響小鈴鐺、TM 名單、電話小結或客訴列表；完成後要回查各相關頁面。
- 若待辦連結到外撥或客訴，應先核對客代與關聯編號；不要只依描述文字處理不同客戶的待辦。

## 5. 空資料、部分失敗與錯誤排查

| 現象 | 先檢查 | 判讀與處理 |
|---|---|---|
| 整頁無法載入 | 登入、權限與待辦查詢服務 | 先區分頁面／API 故障與目前沒有待辦。 |
| 清單為空 | 是否勾選全部、目前客服、日期／頁碼、總筆數 | 先用預設範圍重查；空結果可能是條件未命中。 |
| 看不到某位客服待辦 | 是否具備查看全部權限、是否勾選全部 | 以授權設定為準，不要以一般帳號推論資料遺失。 |
| 完成後仍在清單 | 更新 API 回應、目前頁碼、狀態與同步時間 | 重新查詢並確認是否只是分頁快取；保留待辦識別值。 |
| 待辦關聯客代不一致 | 客代、訂單／客訴編號與目前服務客戶 | 暫停處理，回客戶查詢核對後再操作。 |
| 部分欄位或來源空白 | 待辦主檔、關聯資料與同步時間 | 分開記錄待辦識別與關聯識別，交維運查核。 |
