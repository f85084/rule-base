# 客訴處理

## 一般人員操作入口

**這頁做什麼**：在 `/CustomerComplaint` 查詢客訴，從訂單／銷退建立案件，填反應或完成；`/CustomerComplaint/Add` 與 `/CustomerComplaint/Add/:id` 是新增／重新開啟入口。適用客服與具授權管理職。

**開始前**：準備客代、關聯訂單／銷退單與銷售編號，先確認客戶沒有被另一流程切換。重新開啟已結案案件、補償或完成權限依當期畫面。

**照著做**：

1. 從客訴列表查詢並開啟案件，核對客代、主因、狀態、關聯單號與歷程。預期結果：開啟的是正確案件。
2. 從訂單／銷退明細按【建立客訴】，確認系統帶入的客代、關聯類別與單號。預期結果：表單不帶錯客戶。
3. 填寫主因、解決方式、內容描述與必要欄位，依權限按【反應】或【完成】。預期結果：歷程新增，狀態更新。
4. 送出後回列表／明細查詢；結案案件只有具權限者才能【重新開啟】。預期結果：案件狀態與操作結果一致。

**完成確認與常見問題**：案件編號、客代、關聯資料、狀態與歷程可回查。新增表單帶錯客戶先關閉並從原訂單重進；按鈕停用先按角色／主因判讀；送出不明不要重複建立。

**影響與技術附錄**：反應／完成／重新開啟會寫入客訴歷程，可能產生通知或補償後續；route query 合併、API 與授權細節留在後段。

## 1. 用途、入口與權限視角

客訴處理用來查詢客訴、由訂單／銷退建立客訴、留下處理歷程，以及在授權範圍內反應、完成或重新開啟客訴。現行前端 route 為 `/CustomerComplaint`；新增與重新開啟另使用 `/CustomerComplaint/Add`、`/CustomerComplaint/Add/:id`。

一般專員可處理畫面允許的客訴；一般權限不能重新開啟已結案客訴。OB 人員／OB 主管只會看到 OB 相關主因；若主因為「客服-OB小組【主管】處理」，一般專員只能【反應】，管理權限才可【完成】。完整授權矩陣仍以當期 UI／後端授權為準。

## 2. 正常流程

### 查詢與開啟

1. 從客訴處理頁輸入客訴編號、關聯單號、關聯項次、主因、日期等條件，按【查詢】。
2. 若結果屬另一個客戶，先依畫面提示確認是否切換目前服務客戶，再重新查詢。
3. 開啟目標客訴，先核對客代、關聯訂單／銷退單、銷售編號、主因、狀態與歷程。

### 建立客訴

1. 從訂單或銷退明細的【建立客訴】進入；系統會帶入關聯類別、關聯單號、銷售編號與客代。
2. 直接從新增入口建立時，先選客訴主因與關聯類別；部分主因會要求關聯單號或銷售編號。
3. 填寫解決方式、客訴內容描述、結案反應內容及必要的商品項次。
4. 如需補償，依頁面查詢並選擇折價券／贈品，或輸入得易點數。
5. 按【確定】一次送出；儲存結果回傳後再以客訴編號重查。

### 反應、完成與重新開啟

- 狀態「已指定」可依權限選【反應】或【完成】；兩者都要在歷程備註視窗留下處理內容。
- 【完成】會將狀態改為「已結案」；若透過電郵／簡訊處理，會對客戶送出處理狀況。
- 狀態「已結案」才可【重新開啟】；一般權限按鈕會停用，管理權限才可使用，重新開啟後可編輯緊急指數、解決方式、內容描述與結案反應。

## 3. 欄位、狀態與資料來源

| 欄位／狀態 | 判讀方式 |
|---|---|
| 客訴主因 | 依帳號顯示可用選項；OB 帳號不應自行假設能看到全部主因。 |
| 關聯類別 | `訂單`、`銷退` 或 `無`；由訂單／銷退進入時通常由系統帶入。 |
| 關聯單號／銷售編號 | 非所有客訴都必填，但特定主因會要求；以表單驗證為準。 |
| 解決方式／內容／結案反應 | 建立與重新開啟時的主要處理內容；修改後要重新查明細與歷程。 |
| 已指定／已結案 | 已指定可反應／完成；已結案可依管理權限重新開啟。 |
| 備註方式 | 意見輸入只留歷程；電郵／簡訊會產生對外通知副作用。 |

列表與新增表單是不同資料請求；從訂單／銷退帶入的欄位透過 route query 合併到表單，客訴編號是後續回查的主要鍵。列表成功但表單預設資料或優惠查詢失敗時，先視為單一請求失敗。

## 4. 寫入與副作用

- 建立客訴會新增客訴主檔與初始處理資料；重複點擊可能造成重複客訴，因此按鈕送出期間不可再次點擊。
- 系統會檢查送出時的目前客戶；若目前客戶已變更，會取消建立並提示「客戶已變更」。
- 【反應】與【完成】會新增歷程備註；【完成】另改為已結案。
- 電郵／簡訊會對外送出處理狀況；折價券、贈品或點數是補償措施，成功後需依回應確認，不可只以表單關閉判定成功。
- 由銷退建立的客訴完成後，銷退明細頁只會回到原流程；銷退狀態與客訴狀態要分別查詢。

## 5. 空資料、部分失敗與錯誤排查

| 現象 | 先檢查 | 判讀與處理 |
|---|---|---|
| 查不到客訴 | 客訴／關聯單號、客代、日期、目前服務客戶 | 以客訴編號或單一條件重查；空結果不代表資料已刪除。 |
| 新增表單空白或帶錯客戶 | route 參數、目前服務客代、訂單／銷退關聯 | 關閉表單，回原訂單／銷退明細重新進入。 |
| 儲存被取消 | 是否在送出期間切換客戶或重複點擊 | 先確認是否已產生客訴編號，再決定是否重送，避免重複建立。 |
| 按鈕停用 | 客訴狀態、主因、登入權限 | 依狀態與權限判讀；一般專員不能以其他帳號行為推論可操作。 |
| 電郵／簡訊或補償結果不明 | API 回應、聯繫歷史、客訴歷程與補償資料 | 分別核對客訴、通知與補償結果，不要只看 toast。 |
| 只有部分欄位更新 | 客訴明細、歷程、關聯訂單／銷退 | 以客訴編號和時間交維運查核後端結果，勿重複送出。 |
