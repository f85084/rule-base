# 名單小組管理

本頁對應 `/OutBoundListManagement`，目前不是通用的外呼名單 CRUD，而是單一「沉澱客戶」流程：先用客代檢查資格，再提交回收。需求盤點為 0 筆需求單，因此以下只記錄既有頁面與 API 可證實的行為。

## 入口與權限

- 網站路由：`/OutBoundListManagement`；可由 [website-menus.json](../../../data/sources/csp/website-menus.json) 的 `id: 102` 核對，位於「內部工作管理」。
- 頁面只有「沉澱客戶」分頁，沒有列表、分頁、一般名單編輯或名單小組成員維護功能。不要把「名單小組管理」名稱解讀成 [外呼組別管理](41-外呼組別管理.md) 的同一套功能。
- API 摘要記為登入後可查詢／操作；實際可見性仍由帳號角色與功能權限決定。提交時操作者 ID 由登入授權上下文覆蓋，不接受前端偽造。

## 查詢與回收流程

1. 在「申請客代」輸入唯一上下文 `customerId`。空值先由前端提示，不呼叫 API。
2. 呼叫 `GET api/OutBoundListManagement/CheckPrecipitationCustomer?customerId={customerId}`。後端先查客戶，再確認 `ObCallingStatus` domain 存在「沉澱名單」狀態，接著查最近 30 筆歷程，最後驗證最新歷程是否就是沉澱狀態；通過後回傳客戶名稱。
3. 只有查到 `customerName` 時「提交申請」才可用。呼叫 `POST api/OutBoundListManagement/ApplyPrecipitationCustomerForm`，body 至少承載 `customerId`；controller 會以目前登入者覆蓋 `CurrentUserId`。
4. 成功時以固定 `ActionType.Recycle` 呼叫 Fugo 的 `fugo21.SPX_OB_AGENT_ASS`，將沉澱客戶回收成可再指派狀態；頁面清空 `customerId` 與 `customerName`，供下一次檢查。

## 欄位、驗證與狀態

| 欄位／狀態 | 規則 |
|---|---|
| `customerId` | 唯一查詢／提交上下文；不可空白。檢查成功後才可提交，且提交仍應使用同一客代。 |
| `customerName` | 由檢查 API 回傳，僅作畫面確認與提交按鈕 guard，不是可由使用者編輯的主鍵。 |
| `CurrentUserId` | 由登入者授權上下文寫入 command，前端傳入值不可信。 |
| 沉澱狀態 | 先從 `ObCallingStatus` 找「沉澱名單」設定，再以客戶最近歷程的最新狀態判斷；不是只看客戶是否存在。 |
| 回收結果 | Fugo 回傳碼等於 `1` 才算成功；成功後客戶離開沉澱狀態，進入可再指派狀態。 |

此頁沒有本地申請單、審核狀態、名單列表或額外轉派對象欄位；回收是直接的 Fugo 狀態更新，不要臆測有另一個待審流程。

## 資料邊界、例外與排錯

- 查詢跨越 Fugo／Oracle 客戶主檔 `fugo21.spx_ob_getcustomerbysearch`、`SPX_GETDOMAININFO`（客戶類型與 `ObCallingStatus`）、部門補充查詢，以及歷程 `fugo21.SPX_OB_GETCALLINGLIST_1`。歷程檢查固定取 30 筆、頁 1，這不是可調分頁功能。
- 查無客代、找不到「沉澱名單」狀態，或最新歷程不是沉澱狀態，會分別落在 `NotFound`／`BadRequest` 類錯誤；查詢失敗時維持提交 disabled。
- 回收由 `fugo21.SPX_OB_AGENT_ASS` 執行；回傳碼非 `1` 時轉成 `SystemError`，並沿用 Fugo 回傳訊息。客戶已不在可回收狀態時，應先回到檢查流程，不要重複提交。
- log-map 沒有 NormalLogger 特徵。排錯保留 `customerId`、兩支 API、登入者、時間、Fugo 回傳碼／訊息與 trace/tid；先確認 domain 設定、最新歷程，再確認回收 SP，避免只看畫面名稱判斷。
- 本頁沒有需求單；若要處理一般外呼組別與成員，請改看 [外呼組別管理](41-外呼組別管理.md)，不要在本頁新增未被來源證實的操作。
