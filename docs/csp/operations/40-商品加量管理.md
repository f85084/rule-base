# 商品加量管理

本頁對應 MI 的 `/ProductIncrease`，位於「內部工作管理」。它處理已建立的商品加量案件：查詢一般／OB 清單、分批載入、標記完成、刪除與 Excel 匯出。[商品加量管理需求](../requirements/pages/40-商品加量管理.md) 目前是 0 筆需求單；以下只記錄來源可證實的 API 與邊界，不把其他頁面或歷史需求內容當成此頁現行功能。

## 入口與權限

- 網站路由：`/ProductIncrease`；可由 [website-menus.json](../../../data/sources/csp/website-menus.json) 的 `id: 127` 核對，選單分類為「內部工作管理」。
- API 來源只確認登入後可查詢一般／OB 清單、操作完成／刪除及匯出；沒有提供更細的角色名稱或功能權限矩陣。按鈕是否可用以目前帳號、環境與實際授權為準，不要自行推定只有管理職才能操作。
- 初始的無量通報發生在[接單作業](06-接單作業.md)的商品流程；本頁目前沒有「建立加量申請」或「重新送出申請」API。不要把查詢頁當成申請入口。
- 完成與刪除都會改變資料並通知申請人，執行前先核對案件 `id`、商品與申請人。

## 查詢與分批載入

| 作業 | API | 參數與規則 |
|---|---|---|
| 一般清單 | `GET /api/ProductIncrease/GetProductIncreaseList` | 傳入 `saleNo`、`skip`、`take`。`saleNo` 為 `null` 時不以銷售編號過濾；查詢層無資料時回空集合。 |
| OB 清單 | `GET /api/ProductIncrease/GetProductIncreaseObList` | 同樣傳入 `saleNo`、`skip`、`take`；後端先讀 `SUBCHANNEL` DomainData，再以兩個通路前綴篩選 `MultiSaleNo`。 |

前端頁面以無限捲動方式逐批載入，`skip`／`take` 是後端分批參數，不是另一組 `page`／`pageSize` API。每批回來後，`DataTransform()` 還會補申請人及部、處、組資料；查不到 applicant 時回退原始 mapping 結果，不能把顯示名稱缺失直接判定為案件不存在。

OB 篩選不是在文件中寫死通路編號，而是依 `SUBCHANNEL` DomainData 解析前綴。來源明確指出前綴不足兩筆時會在取值時發生例外；遇到 OB 清單載入失敗，先檢查 DomainData 與回應，不要用一般清單結果代替 OB 清單。

## 欄位與狀態邊界

### 來源可確認的識別與操作欄位

- 查詢使用 `saleNo`、`skip`、`take`；OB 判斷使用 `MultiSaleNo` 前綴。
- 單筆完成與刪除使用加量資料的 `id`；完成流程把目前登入者的 `EmployeeNo` 帶入完成更新。
- 匯出使用布林值 `isSelectOb` 決定是否只輸出 OB 資料。
- 清單顯示會依案件 `id` 查 applicant，再依 applicant 使用者補部、處、組關係；這些是顯示組裝欄位，不是另一個可編輯表單。

### 清單／Excel 欄位

歷史需求快照可核對的清單欄位包括：`#`、申請時間、銷售編號、商品編號、商品名稱、售價、顏色／款式、供應商、商行、處、組、專員；後續快照另記錄通路與 `supplierid`。這些欄位可作為現行畫面與 Excel 的交叉核對線索，但 L1/L2 沒有提供完整 DTO 欄位字典；實際輸出仍以當前 API 回應與 Excel 範本為準。歷史內容只透過 [issues_all.json](../../../data/sources/csp/redmine/issues_all.json) 查閱，不代表本頁新增了其他未被 API 證實的操作。

### 狀態

- `POST /api/ProductIncrease/Done` 會將指定案件標記完成；目前來源沒有提供「取消完成／恢復」API，也沒有另外的狀態碼字典。
- `POST /api/ProductIncrease/DeleteIncrease` 是刪除資料，不是把案件改成另一個可查詢的狀態。刪除後不要假設仍能由本頁復原。
- 完成與刪除的結果可能是失敗訊息／失敗回應；查無商品或查無申請人時不應只重複點擊按鈕。

## 完成：可用量、申請人與通知

`POST /api/ProductIncrease/Done` 的可證實順序如下：

1. 依 `id` 取得商品加量資料。
2. 呼叫 Fugo Oracle `fugo21.spx_QueryProdAvailableqty` 取得可接單量。
3. 取得案件 applicant。
4. 可接單量不為 0 且申請人存在時，寫入完成狀態並帶入完成者。
5. 更新成功後發布 `NoticeUserIntegrationEvent`，通知申請人。

可用量為 0 時，UseCase 會回傳「請確認是否完成加量作業」類型的失敗訊息，不會把 0 量案件當成已完成成功。查無商品、查無申請人或未預期例外也會轉成失敗結果；目前來源沒有定義可用量的數值單位、重試策略或完成後再次顯示加量按鈕的完整規則。

## 刪除與通知副作用

`POST /api/ProductIncrease/DeleteIncrease` 以 `id` 執行：先查商品與 applicant，再刪除 MariaDB 加量資料，並查商品明細後發布通知給申請人。查無商品／申請人時由 UseCase 回傳失敗訊息；商品明細查詢是在刪除後的流程，來源沒有保證它失敗時會回復已完成的刪除，因此應保留 API 回應與時間供追查。

完成與刪除的共同副作用是通知申請人；[MI完整手冊](MI完整手冊.md)也說明申請人的商品有加量時會在鈴鐺出現通知。通知中心的實際文案與導頁行為不應從歷史需求快照直接當成現行固定契約，若使用者未收到通知，請連同案件 `id`、申請人、API 回應與通知中心紀錄一起檢查，參考[通知中心](21-通知中心.md)。

## Excel 匯出

`POST /api/ProductIncrease/DownloadProductIncreaseList` 接受 `isSelectOb`：

- 先以 `GetProductIncreaseAll()` 取得全部案件；勾選 OB 時再依 `SUBCHANNEL` 前綴篩選。
- 匯出前補在職使用者及部、處、組資料，套用 Excel 範本產生 `.xlsx` 附件。
- 回應會設定下載檔名與 `Content-Disposition`，檔名包含當下時間戳。
- 範本不存在或資料組裝失敗時，生成可能直接失敗；不要只依瀏覽器沒有下載判定資料為空。
