# CSP operations 目錄層級規則

本規則適用於本目錄及其子目錄的操作文件編輯。

## 目錄定位

- `operations/` 是 CSP 各功能頁的操作文件集合；每份文件通常對應一個網站功能頁或 route。
- 單頁文件是該頁的完整操作手冊，不是頁面摘要，也不是單純的 API 清單。`README`、索引與摘要表負責導航，不能取代複雜資料流的詳細說明。
- 「完整」不表示每個分頁篇幅相同；凡會影響操作、資料判讀、資料合併、寫入副作用、權限或異常排查的邊界，都要在文件內或可追查的來源中說清楚。

## 單頁手冊最低內容

依頁面複雜度，至少交代：用途與 route、角色／權限視角、正常操作流程、條件與限制、欄位或分頁判讀、資料來源與合併方式、寫入及副作用、空資料／部分失敗／錯誤的排查順序，以及相關文件與來源。跨功能銜接或多來源合併應有獨立段落；摘要表只能作為入口。

## 資料合併與異常邊界

- 明確列出各資料的來源、查詢或寫入入口、合併鍵／優先順序，以及空值、重複、部分成功和單一分頁失敗時的判讀。
- 把頁面整體故障、單一 API／分頁故障、資料尚未同步與條件未命中分開處理；不要用畫面空白直接推論服務故障。
- 寫入操作要說明驗證、目前登入者／權限、後端覆寫、通知或其他副作用；不可自行補上來源未支持的欄位、權限、TTL、保存期限、通知或資料範圍。

## Canonical source 與敘述狀態

- 重要敘述必須能回到適用的 canonical source：現行程式／設定／runtime 證據、`project-docs` 的 L1／L2／api-usage／log-map、需求頁／網站選單、明確的決策文件、現行公告或 Redmine。依敘述類型選最直接的來源並附可追查連結。
- 清楚標示敘述狀態：`現行事實` 是目前來源或 runtime 已確認的行為；`歷史規則` 是舊手冊／舊需求的描述；`推論` 是由來源整理出的判讀；`runtime 未確認` 是來源有描述但尚未在目前環境驗證的行為。
- 來源衝突不可默默選邊；保留衝突與來源範圍，並以現行 UI／API／設定、當期公告或可驗證 runtime 為準。歷史規則與推論不得寫成目前保證，runtime 未確認的細節不得擴寫成契約。

## 編輯檢查

- 先讀本目錄規則、`docs/csp/README.md` 與目標頁的 canonical sources；保留既有 dirty 狀態，只修改任務明確授權的檔案。
- 完成後檢查 Markdown 內部連結與 whitespace，並執行 `git diff --check`；報告列出實際變更、驗證結果與尚未由 runtime 確認的事項。

參考：[`docs/csp/README.md`](../README.md)、[`04-TM名單推薦.md`](04-TM名單推薦.md)。

## 一般讀者與手冊寫法

- 主要讀者是熟悉系統的專員、主管與一般維運；單頁文件要讓讀者先依畫面完成工作，再在需要時追查技術依據。
- 每個功能先交代畫面入口、使用者操作、正常結果與異常時的第一個檢查點。主文優先使用畫面上的欄位、按鈕、分頁與提示文字。
- API、action、程式類別、Repository、DTO、資料庫程序、SSE、cache 等技術名稱集中放在精簡的「維運查核補充」，第一次出現時用一句白話交代用途，不把它們當成一般操作步驟。
- 來源已確認、歷史文件描述、由來源整理的判讀與尚未以 runtime 確認的行為要分開寫；歷史或未確認內容要提醒讀者以當期 UI、公告、回應或授權矩陣為準。
- 白話化不得新增來源未確認的權限、保存期限、TTL、部分失敗策略或成功保證；資料合併、寫入操作者覆寫與異常排查等邊界仍須保留並可回到 canonical source。
