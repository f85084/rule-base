# 審核作業

本篇是 CSP／MI 的通用審核作業入口，對應網站路由 `/Review`。本頁提供待審／已審案件查詢、審核人選擇、批次更新審核結果與審核人調整；實際案件類型的後續處理仍依該功能的操作入口與權限執行。

## 權限與頁面分頁

- 頁面包含查詢區、【待審核】與【已審核】分頁；審核人選單由系統依目前使用者與可代理審核人載入。
- 管理者與一般使用者的待審清單查詢路徑不同。管理者可有「全部」審核人選項；非管理者預設選取目前使用者。
- 已審清單對管理者會回空分頁；若管理者切到已審分頁沒有資料，先確認這是頁面權限規則，不要直接判定資料遺失。
- 審核人調整與結果更新是否顯示，仍以目前帳號可見按鈕與案件權限為準。

## 查詢待審案件

1. 進入【審核作業】，等待審核人清單載入。
2. 依頁面提供條件選擇審核人、申請人、案件類型與分頁條件。
3. 在【待審核】執行查詢；結果會依建立時間由新到舊排序。
4. 開啟案件前核對案件 ID、申請人、目前審核人、類型與狀態。查無資料時保留查詢條件，改查其他條件前先記錄原結果。

## 查詢已審案件

1. 非管理者可切換【已審核】並依審核人、申請人、類型及分頁條件查詢。
2. 已審查詢使用分頁；超出頁碼範圍時可能回空結果，先回到第一頁重新查詢。
3. 管理者查到空分頁時，不要以此頁追查管理者的歷史案件；應回到對應功能的查詢或報表入口確認。

## 更新審核結果

1. 由待審清單選取案件，核對目前狀態與案件類型；批次操作前確認每筆 ID 都屬於目前清單。
2. 送出審核結果時，系統會先依案件 ID 讀取原始資料，再逐筆更新審核狀態。
3. 若結果為 `Approved`，系統會執行該案件類型對應的核准後處理；完成後回查案件狀態與該功能的後續資料，不要只看批次回應。
4. 更新流程有重試機制；連續失敗三次後會回傳「系統繁忙，請稍後再試」，此時先停止重送並保存批次內容、案件 ID 與時間。
5. 更新結果以頁面回應為準；若影響筆數為 0 或回傳失敗，先查詢案件是否已被其他操作更新。

## 調整審核人

1. 從案件操作中開啟審核人調整，選擇目前可用的審核人。
2. 儲存前確認案件 ID、原審核人、新審核人與案件狀態。
3. 修改者由後端以目前登入者覆蓋記錄；更新只改審核人資料，不等同於更新案件審核結果。
4. API 回傳更新筆數為 0／false 時，重新查詢案件與審核人，不要假設已完成指派。

## API 與排錯對照

| 操作 | API | 來源可確認的行為／邊界 |
|---|---|---|
| 待審清單 | `GET /api/Review/QueryReviewList` | 依管理／一般權限走不同查詢；無資料回空清單 |
| 已審清單 | `GET /api/Review/QueryReviewedList` | 使用分頁；管理者直接回空分頁；超出頁碼也可能為空 |
| 審核人清單 | `GET /api/Review/QueryReviewerList` | 依可代理審核人與啟用員工組成；無資料回空集合 |
| 更新狀態 | `POST /api/Review/UpdateReviewStatus` | 先讀原始案件再更新；`Approved` 會觸發核准後處理；失敗重試三次 |
| 更新審核人 | `POST /api/Review/UpdateReviewReviewer` | 修改者由後端寫入；更新筆數為 0 時回傳 false |

## 常見異常

| 現象 | 先檢查 | 處理方式 |
|---|---|---|
| 待審清單為空 | 審核人、申請人、類型、管理／一般權限、資料更新時間 | 以原條件重新查詢；保留條件與案件範圍供追查 |
| 已審清單為空 | 是否為管理者、目前頁碼、分頁範圍 | 管理者空分頁是已知規則；非管理者回第一頁再查詢 |
| 找不到審核人 | 代理關係、員工是否啟用、目前帳號權限 | 先重新載入審核人清單，必要時請管理者確認代理設定 |
| 更新狀態失敗 | 案件 ID、案件是否已被處理、影響筆數、回應訊息 | 先查詢目前狀態；重試三次後停止操作並回報錯誤時間 |
| 核准後續資料未更新 | 回應是否為 Approved、案件類型、核准後處理結果 | 保存案件 ID 與批次結果，交對應功能維運查核，不要重複核准 |
| 審核人更新無效 | 新審核人、案件 ID、回傳影響筆數 | 重新查詢案件；若為 false，記錄原／新審核人與時間 |
